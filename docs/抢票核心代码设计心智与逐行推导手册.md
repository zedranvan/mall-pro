## 一、实体层建模的心智推导

### 1. 核心代码块
```java
@TableId(type = IdType.ASSIGN_ID)
private Long id;

private BigDecimal orderPrice;

private Integer status;

private Integer version;
```

### 2. 设计前的思维推导过程
在写任何实体字段之前，架构师需要考虑三个边界问题：
1. **主键怎么选？** 如果用 `AUTO_INCREMENT`（自增 ID）：
   - 痛点 A：暴露商业秘密（外界通过 `order/1`、`order/2` 能推算平台的实时订单量与流水）；
   - 痛点 B：分布式与高并发插入时，数据库维护自增锁（AUTO-INC 锁）会成为单点吞吐瓶颈。
2. **金额怎么存？** 计算机对浮点数的二进制存储特性决定了 `float` 和 `double` 存在天然精度丢失。
3. **状态怎么表示？** 用布尔值 `isPaid` 还是枚举码？当订单出现退款、关单、发货时，布尔值瞬间失效。

### 3. 修饰符与类型选型解剖
- **`@TableId(type = IdType.ASSIGN_ID)`**
  - **为什么是 ASSIGN_ID？** 采用 MyBatis-Plus 内置的**雪花算法（Snowflake）**。生成 64 位趋势递增的长整型 ID。
  - **为什么类型用 `Long`（包装类）而不用基本类型 `long`？**
    - 基本类型 `long` 默认值为 `0`。MyBatis 在执行新增时，无法通过 `null` 判断字段是否为空，导致自增/雪花 ID 逻辑误判；包装类未赋值时为 `null`，语义明确。
- **`private BigDecimal orderPrice`**
  - **为什么必须是 BigDecimal？**
    - 在 Java 中 `0.1 + 0.2 = 0.30000000000000004`。使用 `BigDecimal` 在底层通过整数数组与标度（scale）模拟人工手算，实现任意精度的财务级定点计算。
- **`private Integer version`**
  - **为什么预留该字段？**
    - 数据库行级数据在被多线程并发修改时，用于作为乐观锁的代次标识。每次成功跃迁版本号必须递增，防止并发覆写（竞态条件）。

## 二、有限状态机（FSM）的防御性设计

### 1. 核心代码块
```java
@Getter
public enum OrderStatus {
    CREATED(0, "待支付"),
    PAID(1, "已支付"),
    SHIPPED(2, "已发货"),
    COMPLETED(3, "已完成"),
    CANCELLED(4, "已取消"),
    REFUNDED(5, "已退款");

    private final int code;
    private final String description;

    public boolean canTransitionTo(OrderStatus target) {
        if (target == null) return false;
        return switch (this) {
            case CREATED -> target == PAID || target == CANCELLED;
            case PAID -> target == SHIPPED || target == REFUNDED;
            case SHIPPED -> target == COMPLETED;
            case COMPLETED, CANCELLED, REFUNDED -> false;
        };
    }
}
```

### 2. 设计前的思维推导过程
在没有状态机约束的初级系统里，状态修改通常散落在各个 Service 中（`order.setStatus(1)`）。
- **致命场景**：网络是不可靠的。假设用户在第 1 秒申请退款（状态进入 `REFUNDED`），但第 0.5 秒发出的第三方支付延迟回调包在第 5 秒才到达，无脑将订单变更为 `PAID`。
- **设计结论**：**状态的流转必须具备“单向受限性”与“闭包自检能力”**。一个实体能跃迁到什么状态，由状态自己说了算，外部代码无权任意指定。

### 3. 修饰符与关键字解剖
- **`private final int code`**
  - **为什么加 `final`？** 枚举常量在 JVM 加载后属于不可变对象。`final` 保证运行期不会被任何反射手段篡改。
- **`switch (this) ->`（Java 17 模式匹配与增强表达式）**
  - **为什么用箭头语法？** 消除传统 `switch-case` 容易漏写 `break` 导致的“穿透（fall-through）”缺陷，编译期严格保障代码分支独立。
- **`case COMPLETED, CANCELLED, REFUNDED -> false;`**
  - **为什么终态全部返回 `false`？**
    - 业务第一性原理：完成、取消、退款属于**终态（Terminal States）**。一旦到达终态，其物理资产（库存已归还、钱已退还）已完成交割，生命周期终止，严禁任何逆向回溯。

## 三、防超卖原子 SQL 的第一性原理

### 1. 核心代码块
```java
@Update("UPDATE d_ticket_category " +
        "SET remain_stock = remain_stock - #{count} " +
        "WHERE id = #{id} AND remain_stock >= #{count}")
int deductStock(@Param("id") Long id, @Param("count") Integer count);
```

### 2. 设计前的方案对比与推导
面对 10 万人抢 100 张门票的场景，业界有三种实现路径：

| 方案 | 实现方式 | 致命缺陷 / 成本 |
| :--- | :--- | :--- |
| **方案 1：应用层查改** | 先在 Java `select` 出库存，`if (stock >= count)` 再 `update` | **必出超卖事故**。并发线程同时查出有库存，全部进入扣减，库存扣为负数（丢失更新）。 |
| **方案 2：分布式锁** | 使用 Redis/Redisson 对 `ticketId` 加分布式锁 | **吞吐量骤降**。锁竞争激烈，网络 RTT 消耗严重，存在死锁与锁续期等高复杂度隐患。 |
| **方案 3：DB 行锁原子减（当前方案）** | 单条 SQL 结合条件判断 | **零超卖、性能最高**。依赖单机存储引擎底层的行级排他锁保证原子性。 |

### 3. 关键字与语法解剖
- **`remain_stock = remain_stock - #{count}`**
  - **为什么不能用 Java 计算出的绝对值（如 `SET remain_stock = 99`）？**
    - 绝对值覆盖会导致“写覆盖”。必须使用相对表达式，让数据库根据当前磁盘最新值进行原子求值。
- **`WHERE id = #{id} AND remain_stock >= #{count}`**
  - **为什么把库存判断写在 WHERE 里？**
    - 当 100 个请求同时冲向这行数据时，PostgreSQL 会为该行加上行排他锁（X 锁）。排在第 1 位的事务修改完后库存变为 0；后续排队的 99 个事务依次获取锁时，数据库会重新评估 `WHERE` 条件。此时发现 `remain_stock >= 1` 不成立，立即跳过该行，不执行更新。
- **返回值 `int`**
  - **为什么必须关注返回值？**
    - 数据库返回受影响行数。返回 `1` 代表抢票成功；返回 `0` 代表条件不匹配（即库存不足），Service 层凭借此返回值作为抛出“手慢了，已售罄”业务异常的唯一铁证。

## 四、Cache-Aside 缓存淘汰策略与序列化选型

### 1. 核心代码块
```java
// 查询缓存
String cachedJson = stringRedisTemplate.opsForValue().get(cacheKey);
if (StringUtils.hasText(cachedJson)) {
    return objectMapper.readValue(cachedJson, TicketCategory.class);
}

// 回填缓存（带兜底 TTL）
stringRedisTemplate.opsForValue().set(cacheKey, json, 1, TimeUnit.HOURS);

// 数据变更时淘汰缓存
stringRedisTemplate.delete(cacheKey);
```

### 2. 设计前的思维推导过程
- **为什么需要 Redis？**
  - 票档信息（如周杰伦内场 1280 元）是**极高频读、极低频写**的数据。数万人疯狂刷新商品详情，每次都查询数据库会导致数据库线程池耗尽崩盘。
- **为什么选 Cache-Aside（旁路缓存）？**
  - 读流程：先查 Redis $\rightarrow$ 命中直接返回 $\rightarrow$ 未命中查 DB $\rightarrow$ 写入 Redis。
  - 写流程：先更数据库 $\rightarrow$ **删除旧缓存**（淘汰）。

### 3. 修饰符与设计细节解剖
- **`StringRedisTemplate` 与 `ObjectMapper`（JSON 字符串）**
  - **为什么不用 `RedisTemplate<Object, Object>` 配合 JDK 二进制序列化？**
    1. **可读性**：在 `redis-cli` 中查看直接是纯文本 JSON，排查线上数据秒级可视；
    2. **安全性**：JDK 原生反序列化存在严重的反序列化漏洞（RCE）；
    3. **跨语言支持**：未来前端或 Python 分析脚本可直接读取 Redis 中的 JSON，不受 Java 类字节码限制。
- **`1, TimeUnit.HOURS`（1 小时绝对过期）**
  - **为什么必须设 TTL？**
    - 内存是昂贵的。如果不设过期时间，冷门演出或历史票档将永远驻留在内存中，最终导致 Redis 发生内存溢出（OOM）。
- **`stringRedisTemplate.delete(cacheKey)`（为什么是淘汰而不是更新？）**
  - **并发写事故推导**：
    假设线程 A 和线程 B 同时修改票档信息。
    `A 写入 DB` $\rightarrow$ `B 写入 DB` $\rightarrow$ `B 写入缓存` $\rightarrow$ `A 网络卡顿后写入缓存`。
    最终结果：数据库是 B 的最新数据，但缓存被 A 的旧数据覆盖，产生**永久数据不一致**。使用 `delete` 淘汰机制，下次读取强制从数据库拉取最新值，将并发冲突概率降到最低。

## 五、事务一致性边界与状态跃迁

### 1. 核心代码块
```java
@Transactional(rollbackFor = Exception.class)
public TicketOrder createOrder(Long userId, Long ticketCategoryId, Integer count) {
    // 1. 原子扣减库存
    boolean deductSuccess = ticketCategoryService.deductStock(ticketCategoryId, count);
    if (!deductSuccess) {
        throw new BusinessException(400, "手慢了，该票档已经售罄！");
    }

    // 2. 插入订单表
    TicketOrder order = TicketOrder.builder()
            .userId(userId)
            .status(OrderStatus.CREATED.getCode())
            .version(1)
            .createTime(LocalDateTime.now())
            .build();
    ticketOrderMapper.insert(order);
    return order;
}
```

### 2. 设计前的思维推导过程
下单业务包含两个跨表的物理动作：
1. 更新 `d_ticket_category`（扣库存）；
2. 插入 `d_ticket_order`（生成订单）。
- **如果这两个动作中间断电、数据库宕机或主键冲突怎么办？**
  如果扣了库存但订单没生成，用户的票凭空消失，这就是典型的资损。

### 3. 注解与异常机制解剖
- **`@Transactional(rollbackFor = Exception.class)`**
  - **为什么必须显式指定 `rollbackFor = Exception.class`？**
    - **这是 Spring 框架的最大隐坑**：默认情况下，`@Transactional` 仅在抛出 `RuntimeException` 或 `Error` 时触发回滚；如果代码中抛出了受检异常（Checked Exception，如 `IOException`、`SQLException`），Spring 默认**不会回滚**！
    - 显式声明 `rollbackFor = Exception.class` 能够覆盖所有异常类型，确保只要流程发生意外，已扣除的库存必须 100% 自动原路回滚。

## 六、定时巡逻与分批削峰策略

### 1. 核心代码块
```java
@Component
public class OrderTimeoutTask {

    @Scheduled(fixedDelay = 10000)
    public void scanAndCancelExpiredOrders() {
        LocalDateTime expireTime = LocalDateTime.now().minusMinutes(15);

        LambdaQueryWrapper<TicketOrder> query = new LambdaQueryWrapper<TicketOrder>()
                .eq(TicketOrder::getStatus, OrderStatus.CREATED.getCode())
                .lt(TicketOrder::getCreateTime, expireTime)
                .last("LIMIT 50");

        List<TicketOrder> expiredOrders = ticketOrderMapper.selectList(query);
        for (TicketOrder order : expiredOrders) {
            orderService.cancelOrder(order.getId(), "超时未支付系统自动关单");
        }
    }
}
```

### 2. 设计前的思维推导过程
用户锁单后 15 分钟未支付，库存需要自愈回归库存池。
- **能不能让前端倒计时结束时由前端发起取消？**
  绝对不行。用户可能直接关掉手机、断网走人，前端请求根本发不出来。必须由服务端后台守护线程做可靠收底。

### 3. 关键字与分页控制解剖
- **`@Scheduled(fixedDelay = 10000)`**
  - **为什么用 `fixedDelay` 而不用 `fixedRate`？**
    - `fixedRate`：按照固定频率触发。如果一次处理超时订单耗时 12 秒，第 10 秒新的任务就会强行启动，导致任务在线程池中堆积，造成线程并发重入与资源耗尽。
    - `fixedDelay`：严格保证**前一次任务执行完毕后，延迟 10 秒**才启动下一次，绝对避免任务堆积。
- **`.last("LIMIT 50")`**
  - **为什么必须硬性限制 50 条？**
    - 应对大促海量超时订单时的**防御性防爆流设计**：如果不带 LIMIT，一次性捞出 10 万条数据全部塞入 JVM 内存，会导致 JVM 堆内存瞬间打满发生 `OutOfMemoryError (OOM)` 宕机；每次抓取 50 笔，分批次小步快跑，平稳释放数据库锁与系统负载。
