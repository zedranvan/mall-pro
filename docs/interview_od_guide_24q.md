### Q2: MySQL 多个人同时修改数据库会发生什么？
- **考点**：并发写锁争抢、脏写（Dirty Write）、丢失更新（Lost Update）、排他锁（X锁）。
- **标准回答**：
  1. **锁争抢与阻塞**：MySQL InnoDB 引擎在执行 `UPDATE` 时默认会对目标记录加**行级排他锁（X锁）**。当多人同时修改同一行时，先获得锁的事务继续执行，后到达的事务会被阻塞，等待前一个事务提交或回滚释放锁（受 `innodb_lock_wait_timeout` 控制，超时抛出 Lock wait timeout exceeded）。
  2. **脏写与更新丢失**：若没有合理控制，后提交的事务会无情覆盖前一个事务的更新，发生“丢失更新”。
  3. **死锁风险**：若多个事务以相反的顺序分别修改多行记录（如事务 A 锁 1 索 2，事务 B 锁 2 索 1），会触发死锁，InnoDB 的死锁检测器会主动回滚其中一个事务。

### Q3: MySQL 联合索引最左匹配原则（走不走索引判断）
- **考点**：B+ 树复合索引结构与查询优化器行为。
- **场景判断**（假设联合索引为 `idx_a_b_c (a, b, c)`）：
  - `WHERE a = 1 AND b = 2` -> **走索引**（走了 a 和 b）。
  - `WHERE a = 1 AND c = 3` -> **走索引**（仅 a 走索引，c 无法走索引，走索引下推 ICP 过滤）。
  - `WHERE b = 2 AND c = 3` -> **不走索引**（缺失最左列 a，全表扫描）。
  - `WHERE a = 1 AND b > 2 AND c = 3` -> **a 走等值索引，b 走范围索引，c 无法走索引**（范围查询导致后续列索引失效）。
  - `WHERE b = 2 AND a = 1` -> **走索引**（MySQL 查询优化器会自动重排条件顺序匹配最左列）。

### Q4: 并发控制有哪几种方式？
- **考点**：悲观锁、乐观锁（CAS）、互斥原语、分布式锁。
- **标准回答**：
  1. **JVM 进程内锁**：`synchronized`（关键字，JVM 层面锁升级）、`ReentrantLock`（JUC API 显式锁，支持可中断、超时与公平/非公平锁）。
  2. **无锁并发（CAS / 乐观并发控制）**：`AtomicInteger`、`LongAdder`，基于 CPU 底层 `cmpxchg` 指令自旋重试。
  3. **数据库行级悲观锁**：`SELECT ... FOR UPDATE`，直接在数据行上加 X 锁，适合高冲突但会严重占用连接池。
  4. **数据库乐观锁**：在表中增加 `version` 或时间戳字段，`UPDATE t SET ..., version = version + 1 WHERE id = ? AND version = ?`，更新影响行数为 0 表示冲突。
  5. **分布式锁**：跨进程场景使用 Redis + Lua / Redisson（SETNX EX + 看门狗自动续期）或 ZooKeeper 临时顺序节点。

### Q5: synchronized 锁和 Lock 锁的区别是什么？
- **考点**：语法层面 vs API 层面、锁特性对比、底层原理。
- **标准回答**：
  1. **实现机制**：`synchronized` 是 Java 关键字，由 JVM 字节码指令（`monitorenter` / `monitorexit`）支持，基于对象头 Mark Word；`Lock` 是 `java.util.concurrent.locks` 包下的接口，基于 AQS（AbstractQueuedSynchronizer）实现。
  2. **灵活性**：`synchronized` 自动获取和释放锁（异常或方法结束退出）；`Lock` 必须手动加锁并在 `finally` 块中调用 `unlock()`，但支持 `tryLock(timeout)` 非阻塞尝试与超时获取。
  3. **中断响应**：`synchronized` 不可中断等待；`Lock` 支持 `lockInterruptibly()` 响应线程中断。
  4. **公平性**：`synchronized` 只能是非公平锁；`ReentrantLock` 构造函数可选择公平锁（FairSync）或非公平锁（NonfairSync）。
  5. **条件唤醒**：`synchronized` 依赖对象的 `wait()`/`notify()` 单一等待队列；`Lock` 可绑定多个 `Condition`，实现精准唤醒特定线程。

### Q6: Spring 核心功能？IOC 原理？手动 new 的对象能不能给 Spring 管理？
- **考点**：IOC 控制反转、DI 依赖注入、Bean 生命周期、动态单例注册。
- **标准回答**：
  1. **核心功能**：IOC（控制反转，容器集中管理对象生命周期与依赖解耦）与 AOP（面向切面编程，基于动态代理实现事务、日志、鉴权）。
  2. **手动 new 的对象如何交给 Spring？**：
     - **答案是肯定的！**
     - **核心做法**：通过获取 Spring 上下文的 `DefaultListableBeanFactory`，调用其 `registerSingleton(String beanName, Object singletonObject)` 方法，直接将外部 new 出来的对象注册进 Spring 的单例池（一级缓存 `singletonObjects`）中。
     - 或者使用 `BeanDefinitionBuilder` 动态构建 BeanDefinition，调用 `registerBeanDefinition` 交给容器实例化。

### Q7: Bean 对象注入方式有哪些？
- **考点**：依赖注入实现方式优劣势对比。
- **标准回答**：
  1. **构造器注入（官方最推荐）**：不可变对象（`final` 修饰），容器实例化时强制初始化，能彻底防止空指针（NPE），并在编译期/启动期提前发现循环依赖。
  2. **Setter 方法注入**：适合可选依赖，先实例化再调用 setter 注入。
  3. **字段注入（`@Autowired` / `@Resource` 直接打在属性上）**：虽然写法最简单，但官方不推荐，因为隐藏了类依赖关系、脱离容器难以进行独立的单元测试（需要反射注入）。

### Q8: Redis 能不能当成消息队列？既然可以为什么还使用 RabbitMQ？
- **考点**：中间件选型、可靠性、消息确认机制与堆积能力。
- **标准回答**：
  1. **Redis 为什么能当 MQ？**：Pub/Sub（无持久化广播）、List（`LPUSH` + `BRPOP` 阻塞队列）、Stream（Redis 5.0+ 支持消费组与 ACK，接近轻量 MQ）。
  2. **为什么生产上不能代替专业 RabbitMQ/Kafka？**：
     - **内存成本与消息堆积**：Redis 消息完全存在内存中，若消费者挂机产生几百万条消息堆积，Redis 内存会被打爆（OOM）；RabbitMQ 和 Kafka 消息持久化在磁盘，支持海量堆积。
     - **消息确认与丢失（ACK 机制）**：RabbitMQ 具备完备的事务确认机制（Publisher Confirm、Consumer Ack、死信队列 DLX、镜像队列高可用）；Redis 异步主从复制存在丢失数据的天然缺陷。
     - **高级功能**：RabbitMQ 支持复杂的路由机制（Direct, Topic, Fanout, Headers）与延迟队列插件，这是 Redis 无法比拟的。

### Q9: 双向链表和单向链表在插入和删除上的效率区别？
- **考点**：基础数据结构时间复杂度。
- **标准回答**：
  1. **如果给定的是目标节点指针（Node node）**：
     - **单向链表**：删除节点必须先从头节点遍历找到其前驱节点（Predecessor），耗时为 $O(N)$。
     - **双向链表**：节点直接持有 `prev` 和 `next` 指针，修改 `node.prev.next = node.next` 和 `node.next.prev = node.prev` 即可，耗时为严格的 $O(1)$。
  2. **如果在链表头部/尾部插入/删除**：两者在维护了 tail 指针的情况下都是 $O(1)$。
  3. **代价对比**：双向链表每个节点需要额外维护一个前驱指针，占用更多的内存空间。

### Q10: 遇到过内存问题吗？怎么排查的？用的什么工具？
- **考点**：JVM 内存模型、生产 OOM 排查流程、排查工具链。
- **标准回答**：
  1. **排查流程**：
     - 在启动参数配置 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/log/dump.hprof`，当发生 OOM 时自动保存现场堆内存镜像。
     - 线上应急先看 CPU 与内存占用：使用 `top -Hp <pid>` 查看高占用线程 ID，使用 `jstack <pid>` 排查死锁或高 CPU 循环。
     - 查看 GC 状况：使用 `jstat -gcutil <pid> 1000` 观察 Old 代占比及 Full GC 频次。
  2. **堆转储文件分析**：
     - 将 `.hprof` 文件拉取到本地，使用 **JProfiler** 或 Eclipse **MAT (Memory Analyzer Tool)** 打开。
     - 查找 **Dominator Tree（支配树）** 和 **Leak Suspects（内存泄露猜想）**，找出占用内存最大的大对象及其 GC Roots 强引用链。
     - 结合项目实战：如我们在数据导出时，因为将海量数据直接查入 List 导致内存被打满，重构为基于游标的分页流式读写，老年代内存占用瞬间降至几十兆。

### Q11: 了解过虚拟线程（Virtual Threads）和协程吗？
- **考点**：Java 21 新特性、线程模型演进。
- **标准回答**：
  1. **概念**：虚拟线程是 Java 21 正式引入的轻量级用户态线程（Project Loom），旨在解决传统平台线程（1:1 映射操作系统内核线程）创建成本高（约 1MB 栈内存）、上下文切换开销大的问题。
  2. **实现机制**：采用 M:N 调度模型。大量虚拟线程被挂载到少量的平台线程（Carrier Thread 载体线程，通常等于 CPU 核心数）上运行。当虚拟线程遇到非阻塞/阻塞式 I/O（如网络请求、数据库查询）时，JVM 会自动将该虚拟线程从载体线程上卸载（Unmount），载体线程继续执行其他任务；当 I/O 返回，JVM 再将其重新挂载（Mount）恢复执行。
  3. **适用场景**：适合高并发、高 I/O 密集型系统（如 RESTful Web 接口）；不适合纯 CPU 密集型计算任务。

### Q13: 算法题：长度为 n 的数组，每次把 m 个连续且相同的数的和替换它们进原数组，直到没有，输出最后数组
- **解法**：**使用栈维护一个二元组 `Pair(val, count)`**。
  - 遍历数组中的每个元素 $x$：
    - 若栈顶元素的数值等于 $x$，将其计数 `count` 加 1；若不等于，将新二元组 `(x, 1)` 压入栈。
    - 检查栈顶：如果 `count == m`，说明满足连续 $m$ 个相同数，将该二元组弹出，计算新数值 $new\_val = x \times m$。
    - 将 $new\_val$ 作为新的输入元素，循环重复上述入栈与合并判断流程，直到无法继续合并。
  - 最后将栈中所有剩余元素按其计数值展开输出。

### Q2: 能讲一下你对数据库表设计或优化上提升性能的经验吗？
- **标准回答**：
  1. **字段类型精简精准**：状态字段使用 `TINYINT`（1字节）替代 `VARCHAR`；时间统一用 `DATETIME` 或整数时间戳；IP 地址采用整数存储；严禁所有列无脑设为 `TEXT`。
  2. **主键设计规避页分裂**：统一采用自增 `BIGINT` 作为聚集索引，保证数据行物理连续追加，避免 UUID 等随机哈希主键导致 B+ 树叶子节点频繁产生分裂与碎片。
  3. **适度反范式冗余**：对于高频展示但不常修改的字段（如订单列表展示商品标题、病历列表展示科室名），适度冗余在主表，避免百万级大表之间的 `JOIN` 关联查询。
  4. **遵循最左匹配建复合索引**：高频查询条件联合建索引（如 `status, create_time`），把高区分度的列排在前面，并尽量通过覆盖索引（Covering Index）消除回表开销。

### Q3: 项目中业务 SQL 非常多非常杂，怎么知道里面是否有影响性能的慢语句？
- **标准回答（标准生产排查三步法）**：
  1. **开启 MySQL 慢查询日志**：
     - 配置 `slow_query_log = ON`；
     - 设置阈值 `long_query_time = 1.0`（耗时超过 1 秒记录）；
     - 开启 `log_queries_not_using_indexes = ON`（记录全表扫描的无索引语句）。
  2. **聚合分析工具提炼 Top 慢查询**：
     - 慢日志积累后文件巨大，使用内置工具 `mysqldumpslow` 聚合分析：
       - `mysqldumpslow -s t -t 10 /var/log/mysql/slow.log`（按总耗时倒序提取前 10 条慢 SQL）。
     - 生产环境通常配合连接池监控（Druid Web 监控台 SQL 监控）或 APM（SkyWalking / Prometheus）实时大屏抓取超慢慢调用。
  3. **EXPLAIN 执行计划剖析**：
     - 拿到具体慢 SQL 在测试库执行 `EXPLAIN SELECT ...`；
     - 重点核对：`type` 是否为 `ALL`（全表扫描）或 `index`（全索引扫描）；`key` 确认实际命中的索引；`Extra` 警惕出现 `Using filesort`（额外文件排序）或 `Using temporary`（产生临时表）。

### Q4: 比如 ArrayList 资源，一般如何保证线程安全？
- **考点**：线程安全集合类选型认知（不单单只有粗暴加锁）。
- **标准回答**：
  1. **`Collections.synchronizedList(new ArrayList<>())`**：在原有 ArrayList 外层包一层装饰器，所有操作加互斥锁，适合读写较均衡的简单并发。
  2. **`CopyOnWriteArrayList`（写时复制容器，读多写少首选）**：
     - 读操作完全无锁（`get` 直接读底层 `volatile` 数组引用），性能极高；
     - 写操作（`add`/`set`）加重入锁，拷贝一份底层原数组进行修改，修改完成后将原引用指向新数组；
     - 缺点：写操作频繁会产生大量数组拷贝内存占用，且存在数据弱一致性（读可能读到旧快照）。
  3. **若场景为并发 Key-Value**：优先选择 `ConcurrentHashMap` 而非 `Hashtable` 或加锁。

---

### Q5: 讲解一下 ConcurrentHashMap 底层原理
- **考点**：JDK 1.8 数据结构、CAS、synchronized 细粒度控制。
- **标准回答**：
  1. **数据结构**：JDK 1.8 放弃了 1.7 的 Segment 分段锁，改用与 HashMap 相同的 **Node 数组 + 单向链表 + 红黑树**（链表长度 $\ge 8$ 且数组容量 $\ge 64$ 转为红黑树）。
  2. **并发控制粒度**：
     - **写操作首节点为空**：使用 **CAS（Compare-And-Swap）** 无锁化原子写入，失败则自旋重试；
     - **写操作节点已有数据（Hash冲突）**：使用 **`synchronized` 仅锁定该桶位的头节点（First Node）**。这意味着并发控制细化到了每一个数组槽位（Bucket），只要并发写入不在同一个槽位，彼此完全无锁竞争。
  3. **读操作**：完全无锁，Node 的 `val` 和 `next` 指针都用 `volatile` 修饰，保证可见性。
  4. **扩容并发协同**：多线程可同时协同参与数据迁移，通过 `ForwardingNode`（Hash 值为 -1）标识已迁移节点，迁移期间读操作转发到新表。

---

### Q6: synchronized 锁一般怎么使用？锁实例还是锁什么？
- **考点**：锁对象头原理、锁的粒度与作用域。
- **标准回答**：
  1. **锁普通方法（锁当前实例对象 `this`）**：两个不同的实例互不影响，若并发调用同一个实例则互斥。
  2. **锁静态方法（锁当前类的 `Class` 对象）**：类锁，全 JVM 单例全局互斥。
  3. **锁代码块（最佳实践，粒度最小化）**：
     - 锁定私有的独立锁对象：`private final Object lock = new Object();`，只保护核心临界区代码，执行完立刻退出。
     - **严禁锁包装类的缓存对象**（如 `synchronized(new Integer(1))` 或 `synchronized("lock")` 字符串常量池），因为全局共享会导致意外的跨模块线程死锁。

### Q7: 做了很多性能优化，怎么判断需要做性能优化的？怎么优化的？（结合秒杀业务）
- **考点**：压测发现瓶颈、数据指标支撑、架构优化步骤。
- **标准回答（结合本地 mall-pro 实操）**：
  1. **如何判断瓶颈**：使用 Python 异步并发模型模拟 1000 用户并发抢购门票，发现单机吞吐量只能跑到 180 QPS，P99 延迟突破 1.2 秒，服务器 CPU 使用率不高，但 HikariCP 连接池等待线程数持续打满超时。
  2. **定位根因**：发现接口上的 `@Transactional` 方法内包含了用户限购规则解析、RPC 校验等耗时计算逻辑，导致事务过大，长时间占有了数据库物理连接。
  3. **具体优化三板斧**：
     - **第一斧（事务细粒度拆解）**：将只读校验与计算剥离到事务之外，仅把最终的库存变更和订单入库包裹在极简小事务中；

     - **第三斧（物理约束兜底）**：数据库层添加 `CHECK(stock >= 0)` 物理约束，彻底杜绝超卖。
  4. **调优结果**：单机 QPS 从 180 跃升至 1049，P99 延迟缩减 55%，数据库连接池无任何积压。

### Q8: 了解 JVM 吗？讲一下 G1 垃圾回收的过程
- **考点**：G1 分区架构、GC 阶段划分。
- **标准回答**：
  1. **Region 架构**：G1 将整个 Java 堆划分为数千个大小相等的独立区域（Region，通常 1MB~32MB）。不再物理隔离年轻代和老年代，每个 Region 可以动态扮演 Eden、Survivor 或 Old，另有专门存储大对象的 Humongous 区域。
  2. **回收四大阶段**：
     - **初始标记（Initial Marking）**：需要短暂停顿（STW），仅标记 GC Roots 能直接关联到的对象，伴随 Young GC 进行，速度极快。
     - **并发标记（Concurrent Marking）**：与用户线程并发运行，从 GC Roots 开始对堆中对象进行全量可达性分析，遍历整个对象图。
     - **最终标记（Remark）**：需要短暂停顿（STW），通过 SATB（原始快照）算法修正并发标记期间由于用户程序运行导致引用变动的对象。
     - **筛选回收（Mixed GC / Cleanup）**：需要短暂停顿（STW）。G1 根据用户设置的预期停顿时间（`-XX:MaxGCPauseMillis`），优先选择垃圾最多、回收价值最高的 Region 进行回收。采用**复制算法**，将存活对象拷贝到空闲 Region 中，清空原 Region，彻底消除内存碎片。

### Q11: 算法题手撕：建图 + DFS 遍历
- **解法框架**：
  - 使用邻接表构建图结构：`Map<Integer, List<Integer>> graph = new HashMap<>();` 或 `List<Integer>[]`；
  - 维护访问标记数组 `boolean[] visited`，防止图中有环引发无限死循环；
  - 编写递归函数 `dfs(int u)`：标记 `visited[u] = true` -> 处理当前节点逻辑 -> 遍历其相邻节点 `for (int v : graph.get(u)) if (!visited[v]) dfs(v);`。
